All callback/provider/returned/finish implementations, measurement registrations and authored batch algorithms remain unchanged. Descending production/prepend and ascending drain are preserved. The size guard, initial LedgerNone fallback and false-shape original query/fold branch are unchanged. Mid-drain LedgerNone reconstructs the complete current node plus rest, invokes the specialized recovery with unchanged columns, and resumes the original recovered cursor loop with full returned context. No stale detached owner is reattached after that continuation.

The exposed Batch/carrier constructors still do not enforce world-hole alignment or a production confinement boundary. This remains a private experimental route; unchanged prefixes do not establish universal authority or refinement.

## Fresh allocation interpretation

Read-only inspection of the independent worker's `/tmp/bendvy-native1024-concrete-{motion,health}-transport-v1/{evidence.json,analysis.json}` and actual C confirms a narrower result than eliminating owner boxes. Each schema still constructs 4,194,304 MainSlots, concrete handoff nodes, FlatPairs and FlatMarks. Motion surviving slot is `batch.c:8898`, Health `:9309`; these allocate class-fit7/class-fit9 respectively while publishing the reconstructed Some into the columns Array. This corresponds to unchanged HA row-return code, Motion `held-adapter.bend:662`, where returned affine row fields reconstruct the nominal MainSlot for `Array.set`. The successful evacuation edge no longer seals a boxed opaque Main owner, but this does not remove the subsequent row-return slot constructor.

Concrete carrier allocation is Motion C4573 (9 logical words) and Health C4893 (11), both class16. The old generic carrier was class4. Across 4,194,304 updates, the extra12 carrier words cost50,331,648 words; removed4,128,768 RFC cells offset that to the observed net +46,202,880 words (+11.015625/update). Requests and RFC fall by4,128,768, while total constructor counts remain equal after normalizing the carrier tag rename. Observed totals are29,758,407 requests/12,677,438 RFC for each schema, with169,438,223 Motion and202,992,655 Health requested words. These are the independent worker's actual allocation observations, not timing or this reviewer's rerun.

One bounded fallback if raw results show the wider carrier loses is to restore the original generic opaque carrier independently for the affected schema, retaining the same two-phase source algorithm, callbacks, guard and recovery. That is a representation rollback to the verified v8 path, not a claim of another optimization: it trades the owner RFC back for class4 nodes and avoids speculative scalar packing or changes to arbitrary Type ownership. The surviving row-return constructor belongs to persistent column publication, so merely adding an erased helper or changing producer names does not justify claiming its removal. A different persistent storage representation would require a separate design and full payload/recovery gates. No second candidate is proposed for implementation before the raw results.

## Conditional split-ID alternative, not implemented

A separate Motion-only probe could remove `id` from the concrete node and thread an owned `Array<U32>` plus selected count through producer, batch, drain and recovery. Motion owner7+tail1 yields8 logical words/class8; Health owner9+tail1 remains class16, so this argument does not justify a Health probe. Current Native `blk_new` initializes flat buffer storage, and U32 Array accesses carry scalar elements without an opaque owner RFC. This is a source-supported representation hypothesis, not a measured outcome.

Allocate/inspect the ID buffer before any Main evacuation. Require its actual physical `Array.size` at least declared capacity; never trust metadata depth alone. Its constructor initialization and every guard/read/write must remain inside actual workload accounting. Descending scan writes successful Some IDs at `count`, increments count only for that successful evacuation, and prepends its owner. Ascending drain reads `count-1` for the head and decrements exactly once per Con. None/missing/excluded rows must neither write IDs nor increment count. Because successful IDs are unique and within capacity, the producer's selected count is bounded by capacity; this bound must remain tied to the existing Main size and logical-index checks.

Mid-drain LedgerNone must restore the current and all remaining owners using those same descending-buffer indices, accumulate ascending logical IDs, then pass them to the unchanged original cursor continuation. Full nonidentity returned context, selected handle namespace/id, pending Pair flush, true-old journal order and immutable cached views remain unchanged. Initial missing-ledger or buffer/Main size failure uses the original route before detachment.

This is safe only under the private producer-to-consumer invariant linking owner-list length to count and the initialized ID prefix. Arbitrarily constructed exported Batch values can violate it; a Nil/count or Con/count mismatch check cannot recover missing IDs after detachment and must not be advertised as a universal safe fallback. Production confinement remains unresolved. Fresh malformed-ID/capacity controls should exercise the preflight entry, not fabricate unrecoverable detached batches and claim successful recovery.

Smallest admission sequence: checker/emitter demonstrate actual class8 carrier and flat scalar buffer; fresh complete65 Motion fields and allocation/word attribution including buffer setup; then multi-ID ascending Required/Present/Absent/Optional, holes/high/zero/empty, undersized physical ID/Main arrays, initial/mid-ledger None recovery, owned raw/cache discrepancies and nonidentity fallback, plus actual wrong-ID/count/reverse/missing-restoration mutants. No implementation or second-candidate enrollment is authorized by this note. Await current wide-carrier raw results and root's explicit next decision.
