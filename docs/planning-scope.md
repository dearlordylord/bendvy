# Bendvy: рамка планирования и интервью

**Черновик для обсуждения, не утверждённый план реализации.** Основан на [общей схеме](development-roadmap.md) и двух независимых разборах Астры. Реализацию и технические эксперименты пока не начинаем.

## Согласовано в интервью

- Конечная цель — весь core зафиксированного bevy-ts. Ограничения Bend2 и расхождения согласуем отдельно; они не уменьшают скоуп автоматически.
- Подробно планируем ближайшие проверки; остальные блоки сохраняем в общей карте.
- Первый сценарий — простая симуляция: сущности появляются, движутся к цели, получают урон и удаляются; события сообщают о попаданиях и гибели.
- Первая среда — консольная программа на CPU, фиксированный шаг, воспроизводимый результат. Выбираем самые простые варианты; численные критерии приёмки ещё определим.
- Схему сначала описываем явными типами и составом мира, без отдельного DSL/генератора; типобезопасность сохраняем.
- Каждое упрощение явно сопровождаем follow-up с причиной и условием возврата: [реестр](follow-ups.md). Ограничение компонентов только Data не согласовано; учитываем ECS и performance при выборе представления.
- Незаявленный доступ системы и запись через read должны отвергаться при проверке Bend; подтверждаем это отрицательными compile cases, не только корректными примерами.
- API и storage проектируем под типовую систему, affine ownership и runtime Bend, сохраняя ECS-контракты. TS-представления не копируем автоматически; корректность выбранных конструкций и runtime-стоимость проверяем отдельно. Ограничения языка не обходим небезопасными casts или разделением ownership ради внешнего сходства API.
- Последующая внешняя проверка — Tower Defense `canonical-defense` из `/workspace/typescript/jev`; включение игры в репозиторий Bendvy пока не предполагается. Объём проверки и способ интеграции ещё обсуждаем.
- При внешней проверке сначала используем ECS для игровых сущностей/систем, сохраняя авторитетный reducer `Canonical.step`. Оригинальный `/workspace/typescript/jev` не меняем: нужные исходники разрешено копировать в отдельную рабочую директорию; единую копию и синхронизацию с оригиналом не требуем.
- Требование performance: сборки Bend в низкоуровневые языки должны существенно превосходить bevy-ts; JavaScript-сборка должна быть как минимум сравнимой. На ближайшем этапе измеряем native CPU и JS на одинаковых нагрузках, включая память, копирования и traversal/update. Численный коэффициент native-ускорения и допуск JS-сравнимости ещё не установлены; это обязательства конечного результата, а не уже достигнутые показатели. Превосходство над Rust Bevy не требуется.
- Процесс доказательств — best practices [bend-ldd](/home/node/.codex/skills/bend-ldd/SKILL.md): кандидатные законы с объяснением → falsification и контроль посаженным дефектом → согласование конкретных законов → доказательства → мутанты. Выбор процесса не означает одобрение ещё не написанных законов.

## Процесс проверки по bend-ldd

- Для каждого блока формулируем точные гарантии, включая полноту результата, соответствие простой спецификации, сохранение остальных данных, bounds и свойства helpers. Применимость каждого свойства обсуждаем; порядок ECS не объявляем несущественным автоматически.
- Чистая логика относится к проверяемому ядру; IO и внешние эффекты — к host. Примерные сценарии и сверка TS/Bend дополняют доказательства.
- До доказательств показываем человеку формулировки законов, их смысл, результаты falsification и найденные неоднозначности. Только согласованные законы становятся обязательством.
- Используем gate `bend PROOF.bend --verdict` и mutant checks; каждый checker run ограничен 5 секундами. Timeout требует пересмотра формы, skipped/undecided проверки не считаем успехом.
- Каждому закону нужен осмысленный компилируемый mutant: экземпляр закона верен на исходном core, неверен на mutant, proof отвергается в соответствующем разделе. Эквивалентные мутанты и пробелы отчёта разбираем отдельно.
- Факты сначала ищем в Base/mathlib; mathlib не импортируем в production core. Совместимость lawcheck/bend-falsify с выбранным Bend проверяем при подготовке инструментов. Указанная в skill проблема lawcheck на 2.0.32 не устанавливает его статус на нашей версии.
- Установка новых зависимостей — отдельный шаг согласования по skill; пока ничего не устанавливаем.

## Внешний сценарий: результат исследования

Астра обнаружила несколько игр в `jev`: текущая — [`canonical-defense`](/workspace/typescript/jev/prototypes/canonical-defense/README.md), прежняя боевая — [`bend-tower-defense`](/workspace/typescript/jev/prototypes/bend-tower-defense/Model.bend). Обе используют Bend; имя родительского каталога `typescript` не определяет язык игры.

Для внешней проверки выбран canonical-вариант. Он использует собственное состояние и reducer, значимый порядок tick, связи parent/sibling, ресурсы/ledger, fixed timestep и lifecycle cleanup. Это кандидатные интеграционные проверки, не автоматически принятые требования первого среза. Исходники не изменялись, измерения не повторялись.

## Глубина планирования

Подробные задачи ближайшего горизонта: [план проверок](next-stage-plan.md).

| Горизонт | Что планируем | Условие перехода |
|---|---|---|
| Вся цель | Обязательные контракты ECS, границы паритета и доказательств, зависимости, допустимые расхождения | Общее понимание цели и критериев завершения |
| Ближайший — подробно | Фиксация Bend/base; две схемы; неверный read/write-доступ; повторный запуск; владение, минимальный rollback и visibility | Проверки подтверждают совместимость API записи, storage и транзакции |
| Следующий — структурно | Headless-сценарий: entities, query, resource, schedule, commands и markers | План реализации уточняем по результатам ближайших проверок |
| Последующие — крупно | Relations/scopes, states, composition/provisioning, snapshots/validation/debug; math/input/adapters | Для каждого блока: входные зависимости, acceptance и условие возврата в подробное планирование |
| Оптимизации | Storage/cache, parallel compute | Воспроизводимые нагрузки и измерения |

Полный перечень остаётся в таблице паритета. Отложенное не считается отменённым; согласованное расхождение не считается достигнутым паритетом.

## Масштаб решений

Оценка Астры: **10–14 связанных групп, несколько десятков уточнений**. Это ориентир для интервью, не точный подсчёт задач.

| Группа | Цена пересмотра / что затрагивает |
|---|---|
| Цель, паритет и критерии успеха | Весь объём проекта |
| Первая программа, backend и обязательные ограничения | Критерии проверок и приоритеты |
| Schema, данные Data/Type и capabilities | Публичный API компонентов и queries |
| Identity, reservation, reuse и порядок | Allocator, lookup, relations, snapshots |
| Commit/rollback, ошибки и host IO | Модель записи, storage, публикации |
| Visibility, время и cursors | Runner, events, change detection, lag |
| Schedule, composition и provisioning | Повторный запуск, зависимости, типы ошибок |
| Storage и traversal | Владение, транзакции, стоимость операций |
| Relations/scopes и cleanup | Commands и lifecycle |
| State transitions | Порядок барьеров, enter/exit и границы failure |
| Snapshot, validation, inspection и proofs | Граница наблюдений, восстановления и гарантий |
| Platform и parallel compute | Граница расширений и требования к данным |

Самые дорогие ранние связки: **данные/capabilities ↔ system API ↔ ownership/storage ↔ rollback**, а также **identity ↔ порядок ↔ cursors/barriers**.

Полную реализацию поздних блоков откладываем, их влияние на ранние контракты выясняем сейчас. До закрепления API нужен сценарий: успешная система сохраняет запись; следующая читает собственные записи, создаёт event/command и падает; её изменения и публикации отменяются, предыдущие сохраняются, reader cursor не продвигается. Нужна также ранняя проверка минимальной composition/provisioning.

Границы state-transition failure и восстановления snapshots исследуем отдельно: не предполагаем rollback всей schedule или восстановление всего Runtime.

## О чём спрашивать в grilling

Пользователь определяет цель, желаемое поведение, приоритеты и допустимые ограничения. Факты языка и upstream выясняют агенты; выразимость и стоимость проверяем экспериментами. Выбор journal/delta, schema DSL и cache выносим на обсуждение только при выявленном компромиссе для требований.

Дерево раундов:

1. **Конечное обязательство:** что означает завершённый порт и как учитываем ограничения/расхождения.
2. **Первое применение:** законченная программа и обязательные условия её работы.
3. **Требования:** допустимые ограничения данных и доступа, host boundary, приоритет и объём доказательств.
4. **Семантические развилки:** только неоднозначные или отличающиеся от выбранного upstream контракты.
5. **Технические компромиссы:** после чтения исходников и проверок языка; затем подтверждение общего понимания и подробного ближайшего плана.

Это порядок зависимостей, а не фиксированное число раундов. В каждом раунде задаём все вопросы с уже определёнными предпосылками; зависимые переносим дальше. Уже согласованное повторно не открываем.

**Начальная область интервью:** уточнить обязательство относительно полного core bevy-ts; полный Rust engine уже исключён. Если полный core parity уже согласован, сразу перейти к первому применению. Пока не спрашивать о конкретном storage, ID reuse, DSL или GPU scheduler.
