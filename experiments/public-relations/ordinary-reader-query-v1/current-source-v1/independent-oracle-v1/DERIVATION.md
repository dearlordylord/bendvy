# Current-source normal oracle

`normal-expected.stdout` is generated by `model.py` from the existing normal
Workshop source model, not from a candidate execution. Before applying the
current-source mapping, the model verifies that its copied baseline source
(`base-model.py.source`) reproduces the earlier 15,356-byte Workshop golden
exactly. The generator then checks all 37 source rows in the frozen current
source manifest and verifies that the original normal operation suffix is
unchanged.

The source change exposes two independent identities for the failure reader.
World system registration starts with the fixture's existing system and then
registers `ParentWriter`, `ParentInverse`, and `ParentFailures`, so the failure
system retains registry id 4. Separately, `K.start` initializes the relation
failure reader allocator at 1. A successful `K.register` retains the returned
system registry in the Reader while using the allocator value as `Reader.id`,
then advances `nextReader` to 2. The current consumer's `FailureView` observes
both fields. Consequently, failure Domain membership and event `Position`
serialize reader id 1, while the FailureView's nested RegistryView continues
to serialize system id 4. Every snapshot includes the post-registration
`nextReader=2` value.

The original normal operation sequence and output observations are otherwise
modeled by the prior finite source model. The expected stream uses the module
namespace implied by the current frozen entrypoint's relative import paths.
`selftest.py` checks source pins, the original baseline golden, the exact
current expected bytes, the split registry/reader identities, nextReader,
and unchanged operation source. It does not invoke Bend, Node, or a backend.

This oracle covers only the current normal Workshop scenario. The replacement/
unrelate and distinct SystemFailure scenarios remain to be rebound. It makes no
runtime, TypeScript physical-ID parity, universal-proof, performance, or
issue-level acceptance claim.
