## Where the selection enters keys

In stage/core/inspector-query.bend, grant_composed builds each/get closures from erased selection and WorldRead. The get path is composed_lookup -> composed_lookup_target -> composed_lookup_valid -> composed_lookup_matched -> composed_lookup_projected. The first two have erased H/S/V/selection/world; valid and matched have erased H/S/V/selection. MissingEntity is decided before matches; QueryMismatch before project; the current owner returned by each earlier operation is the next operation's owner.

The same closed selection is therefore supplied to four distinct template definitions, but world only to the first two. Crucially, matches_field and project_field in inspector-query-projection.bend take the selection as a **runtime** argument. Their erased key contains H/S/V, not the selection's callback body. A count of project_field specializations cannot by itself demonstrate duplicated callback-body keys.

family-witness builds four family selections into three nested Product pairs, then constrain with predicate conjunctions. runtime-declarations supplies the complete declaration matrix; owner-carrier wraps ordinary Frame into InspectOwner/CheckOwner and back. In the latter, inspect_granted/check_granted and inspect_get/check_get again take the whole composed grant as an erased cap. inspect_selection/check_selection wrap extracted operations in erased inspect_target/check_target partial applications. These are explicit additional key-bearing boundaries, not a measured ranking of expensive ones.

## What the installed cache actually does

The exact extracted installed source has one def_inst call site, in term_infer's template Ref handling (line2614). def_inst (2916) runs tele_check before cache lookup; term_lower recursively lowers erased arguments, and term_key (692) JSON-serializes the resulting term omitting only source-location field s. The cache is book.tmps[definitionName], keyed by the joined erased terms. A repeated identical key within one template reuses its body, but still incurs argument checking/key construction. Identical erased values passed to different template names do not share instantiated bodies. No observed key for this full47 subject exceeds32768; no key lengths are inferred here.

**Native fixed-point passes do not call def_inst again.** compile_book (5160) emits the already reachable done_defs each pass, retaining own/hot/stat until their combined size stops changing. Its loop calls emit_open/emit_body, not template inference. Archived diagnostic outer census is5941 definitions with identical identities/order across passes1–3; fact sums grow8131 ->8149 ->8157. Thus the source supports frontend repeated key work and a potentially larger graph subsequently re-emitted. It does not support attributing per-pass delay to repeated key serialization or calling fact growth new specialization growth. The marker composed_lookup_valid~46 contains no erased-key payload, so index46 cannot be mapped to a concrete selection/schema/owner from the retained marker alone. A last-started definition is not a cost ranking.

## One next candidate, with a limited rationale

Replace only composed_lookup_target's call to the two erased-selection staging helpers with nested matches over the existing world-valid and selection-matches returned pairs. After valid=False return composed_missing. After valid=True call existing matches_field once; after matches=False return composed_mismatched; after matches=True call existing project_field once and composed_lookup_projected. Thread the returned arbitrary affine H through the nested cases. Retain composed_lookup_valid/matched and every existing public/compatibility signature unchanged; enumeration, pair composition, projection callbacks, all actual Value fields and declaration authority stay unchanged.

This source change would remove the valid/matched helper applications from that reachable lookup route, rather than extracting four pair callbacks (failed24434) or the consumer's three runtime continuations (source/JS passed but Native still failed). It introduces neither a new runtime callback parameter nor duplicate consumption of a callback. It gives a specific structural expectation: no valid/matched specializations reached solely through the ordinary grant get path. Other callers may retain them, and the Native compiler can already inline these calls; fewer source helper applications do not establish lower emission cost. The proposal is therefore a small graph discriminator, not a demonstrated remedy or an authorization to run it.
