# Physical lifecycle oracle derivation

This oracle derives the full `report` output of the frozen current-source fixture. It does not read compiler output, runtime output, receipts, or generated artifacts. The 136 logical records are reused byte-for-byte from the earlier independent TypeScript lifecycle model; this model independently derives every physical record and the enclosing JSON/terminal newline.

The logical artifact is `feature-timing-v1/independent-oracle-v1/expected-scale-1.stdout` (24,298 bytes, SHA-256 `21111a66fe196fc3c9615eadc8a39648c3583a695b233fd3d78eda355693cd60`). Its source model and notes are separately pinned in `SOURCE-BASIS.json`. The current fixture’s source join binds 13 import-only relocations and exactly two diagnostic-rendering body changes, `dump.bend` and `union.bend`; `logical-main.bend` and all lifecycle operation bodies are unchanged. The added `M.Initial` render arms are exhaustive formatting paths but are not reached: this fixture’s setup publishes `M.Transition` values, and no operation applies `M.initial`.

Each schema is a fresh call to `Setup.build`, so its physical world starts at namespace 1, clock 0, and reader/system IDs local to that World. The setup sequence is source-visible: edge publication and barrier advance the World to 1; the initial machine requests start at 2; their barrier advances to 3; the event reader registers and warms at that World clock; transition application advances to 4 and publishes `Flow 4→7` and `Level 10→11`; the rejected Parent cycle and its barrier advance to 5; pending machine requests reserve entity 4 and enqueue its activation, advancing to 6. The world therefore has three live entities, a fourth reserved entity, one deferred command, the two accepted edges for each relation, the cycle-failure notice, and both machine transitions.

The 16 relation cases per schema run in source order. Each has two distinct `I.Fresh` inspections; each successful inspection advances the World clock once. The pair of registered no-op checks adds two `RegistrationMeta` entries but no World-clock advance. Thus categories start at clock 6 and finish at clock 38, with 32 fresh inspectors and 32 check registrations. The first and second machine inspectors then return `Active(39,38)` and `Active(40,39)`. The tracked machine condition registers system 34 at cursor 40 without advancing the World clock, producing `nextSystem=35` and final clock 40. The actual event reader uses untracked `Sys.run`, so its `Registry.cursor` remains 0.

The event-runtime and machine-stream cursors are independent domains. `Ev.start` begins at event tick 0. The warm registered read advances to tick 1, activates the event position at 0, and commits it at cursor 1 after observing the two original notices. The later category `Read.map_world` advances the event runtime to tick 2 and synchronizes the already-published relation-cycle failure as a second retained batch. The condition `Read.map_world` advances the event tick to 3 but publishes no additional World notice. The final registered read runs at tick 4, observes the retained failure, and commits event position `[1:4:0]`. Separately, the warm machine reader is activated/completed at World clock 3; transitions are published to its queues at tick 4, and the final read advances both machine positions to cursor 40 while retaining `registeredAt=3`. Each `Read.map_world` preserves the returned World while advancing only the event-runtime tick.

Physical World strings are rendered from the source field order in `dump.bend`: namespace, allocator IDs and live tree, capacity/depth, component store, relation graph and inverses, resources and machine queues, World notices, pending count, registrations, next system ID, and World clock. The model uses the array/tree shape constructed by `Array.new`/`State.Resources` and renders all retained graph edges, inverse sources, machine queue batches/positions, World registration metadata, and event-runtime batches/positions. Each category inspection contains its full physical World snapshot; each machine operation contains the complete `EventRuntime` owner snapshot, its separate registered `Registry` owner, and the warm result.

The implementation is a source-derived model, not a claim that physical dumps are cross-backend identical in general. It binds the one frozen lifecycle and its physical projection, with the independent logical record oracle retained as a separately scoped input. Full feature timing, performance, and general physical-equivalence claims are outside this artifact.
